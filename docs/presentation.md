# 答辩演示脚本

> 总时长控制在 12–15 分钟，留 5 分钟答疑。
> 演示前 5 分钟完成"演示前检查清单"，避免现场起服务。

## 一、演示前检查清单

| 项 | 命令 / 操作 | 预期 |
|---|---|---|
| MySQL | 确认 `MySQL80` 服务运行 | `Get-Service MySQL80` 状态 Running |
| 后端 | `$env:JAVA_HOME='C:\Program Files\Java\jdk-25'; cd backend; D:\maven\bin\mvn.cmd spring-boot:run` | 8081 启动，日志出现「初始化默认账号完成」 |
| 前端 | `cd frontend; npm run dev` | 5173 可访问 |
| 数据 | 用 `admin` 登录，记录页至少保留 5 条不同月份的记录 | 看板折线非空、饼图有多个分类 |
| 浏览器 | 打开两个标签页：`/login` 与 `/dashboard`；缩放 100%，窗口最大化 | 布局正常（侧边栏 220px + 内容区撑满） |
| 备用 | 截图备份 `docs/screenshots/`，万一服务异常可直接讲图 | — |

> 演示中如需重置数据，重新执行 `schema.sql` + `data.sql` 后重启后端即可，账号会自动重建。

## 二、演示流程（共 14 分钟）

### 第 1 段：工程介绍（2 分钟）

**操作**：停留在 `docs/README.md` 或直接讲，不切页面。

**讲解要点**：

- 一句话定位：前后端分离的"后台权限管理 + 财务收支记账"系统。
- 技术栈：后端 Spring Boot 3.5 + MyBatis-Plus + MySQL 8 + Spring Security + JWT；前端 Vue 3 + TypeScript + Element Plus + Pinia + ECharts。
- 开发方式：以 OpenSpec 规范文档为唯一事实来源，6 份能力 spec 作为验收契约，AI 生成约 80% 代码。
- 目录：`backend/`、`frontend/`、`docs/`、`openspec/` 四部分。

**建议话术**：
「整个项目的需求不是直接写代码，而是先固化成 OpenSpec 文档：提案、设计决策、任务清单，再拆成 6 份能力 spec。每份 spec 里的 scenario 就是我的验收清单，最后测试报告的 44 条用例就是从这些 scenario 来的。」

### 第 2 段：登录与 RBAC（4 分钟）

#### 2.1 登录与 JWT（1 分钟）

**操作**：

1. 在 `/login` 输入错误密码 → 提示「用户名或密码错误」，HTTP 401。
2. 输入 `admin / admin123` → 跳转首页，右上角显示「管理员」。

**讲解要点**：

- 密码 BCrypt 哈希存储，数据库里看不到明文；错误提示不区分"用户不存在"和"密码错误"，避免探测账号。
- 登录成功签发 HS256 令牌，payload 含 userId/username，有效期 2 小时；后续请求由过滤器解析注入 SecurityContext。
- 令牌失效 → 401，前端拦截器自动清 token 跳登录页。

#### 2.2 权限配置链路（2 分钟）

**操作**（按"角色 → 菜单 → 用户"的顺序讲，体现三元模型）：

1. 打开 **菜单管理**：展示树形结构，指出三类节点（目录/菜单/按钮），按钮节点带 `perms` 如 `finance:record:export`。
2. 打开 **角色管理** → 点「权限分配」→ 展示勾选树（含按钮节点）→ 不做修改直接关闭（避免影响演示数据）。
3. 打开 **用户管理**：展示用户列表，指出新增/编辑对话框里有「角色」下拉。

**讲解要点**：

- RBAC 五表模型：user / role / menu + 两个关联表。
- 权限标识在 `sys_menu.perms`，后端 `@PreAuthorize("@ss.hasPermi('finance:record:export')")` 与前端 `hasPerm()` 用的是同一个字符串，三处一致。
- 侧边栏不是写死的，是登录后 `GET /api/auth/info` 返回菜单树动态渲染的。

#### 2.3 权限隔离实证（1 分钟）

**操作**：

1. 退出，用 `user / user123` 登录。
2. 观察侧边栏：只有「首页」「财务管理」，没有「系统管理」「审计日志」。
3. 地址栏手动输入 `http://localhost:5173/system/users` → 被重定向回可访问页面（路由守卫拦截）。

**讲解要点**：

- 前端拦一层（菜单不渲染 + 路由守卫），后端再拦一层（403）。绕过前端直接调接口也拿不到数据，这是"按钮级权限"的核心。

### 第 3 段：财务模块（3.5 分钟）

用 `user / user123` 继续，体现普通用户视角。

#### 3.1 收支分类（0.5 分钟）

**操作**：进入 **收支分类**，切换「收入分类 / 支出分类」，新增一个分类，再尝试删除一个已被记录引用的分类。

**讲解要点**：删除被引用分类会被拒绝并提示，防止记录失去分类归属。

#### 3.2 收支记录与多条件筛选（2 分钟）

**操作**：

1. 进入 **收支记录**，展示顶部三张统计卡片（收入/支出/结余）。
2. 点「新增收支」，填类型=支出、分类=餐饮、金额=88.88、日期=今天、备注=答辩演示 → 保存。
3. 观察列表新增该条，**统计卡片与列表同时刷新**。
4. 依次演示筛选：点「今天」→ 点「本月」→ 类型选「支出」→ 分类选「餐饮」→ 备注输入「答辩」→ 逐级收敛结果。
5. 重点：类型选「支出」时，统计卡片里的收入变为 0、结余变负 —— 说明统计与列表口径完全一致。
6. 金额精度：指出 88.88 保存后仍是 88.88，后端 BigDecimal + DECIMAL(12,2)。

**讲解要点**：

- 新增时 `user_id` 由后端强制写入当前登录用户，前端无法伪造归属。
- 普通用户只能看到自己的记录，管理员能看全部 —— 这个隔离规则在列表、统计、导出、看板四个入口共用同一个方法。

#### 3.3 批量操作与导出（1 分钟）

**操作**：

1. 勾选 2–3 条记录 → 顶部出现「批量删除」「批量导出」可用。
2. 点「批量导出」→ 下载 xlsx → 打开展示列（日期/类型/分类/金额/备注）与金额格式。
3. 再点「导出筛选结果」说明按当前条件导出；点「全量导出」说明导出全部（仍受权限范围限制）。

**讲解要点**：三个导出入口共用一个接口，靠 `ids` / `exportAll` / 筛选条件三态区分；文件名用 UTF-8 编码避免中文乱码。

### 第 4 段：加分项演示（3 分钟）

#### 4.1 数据看板（1 分钟）

**操作**：回到首页，展示三个图表。

**讲解要点**：

- 近 12 月折线：收入与支出双线，空档月份补 0（后端补齐 12 个点，避免 x 轴跳月）。
- 近 7 日折线：日粒度对比。
- 分类金额占比环形图。
- 刚才新增的记录已经反映在图表里，数据来自真实业务表，不是假数据。

**主动说明缺口**：看板目前没有时间范围/类型筛选控件，`/dashboard/stats` 也不接受筛选参数，这是 spec 中尚未实现的一项，已在测试报告里记录为已知缺口。

#### 4.2 软删除与操作日志（1.5 分钟）

**操作**：

1. 切到 `admin`，进入 **审计日志**。
2. 展示日志列表：操作人、模块、业务类型（新增/修改/删除/导出/登录）、请求方法+URL、参数摘要、状态、IP、耗时。
3. 指出刚才演示产生的日志：新增记录（成功）、删除被引用分类（失败，状态=失败且有错误信息）。
4. 按 `title=收支记录` + `businessType=删除` 筛选，演示条件查询。

**讲解要点**：

- 日志由 `@OperLog` 注解 + AOP 切面自动记录，成功和失败都记（`finally` 落库），参数里 password 脱敏为 `***`。
- 删除是逻辑删除：数据库 `is_deleted=1`，列表、统计、导出、看板全部不统计已删除数据。
- 日志写入失败不影响业务（catch 后忽略）。

#### 4.3 响应码规范（0.5 分钟）

**操作**：口头说明，不必现场敲命令。

**讲解要点**：401 未认证、403 无权限、400 参数/业务校验失败、500 系统异常，HTTP 状态码与 `body.code` 保持一致，前端据此统一处理。

### 第 5 段：OpenSpec 文档讲解（1 分钟）

**操作**：打开 `openspec/changes/ledger-admin-system/` 目录。

**讲解要点**：

- `proposal.md`：为什么做、做什么、影响范围、非目标。
- `design.md`：10 条设计决策（D1–D10），每条都有"选择理由 + 备选方案 + 权衡"。
- `tasks.md`：6 个阶段 28 项任务，逐项可勾选。
- `specs/`：6 份能力 spec，每个 Requirement 带 WHEN/THEN 场景，这是测试用例的来源。

**建议话术**：
「这套文档不是事后补的，是开发前写的。比如 design.md 里 D5 明确写了'前端静态注册路由 + meta.perm 守卫'，我在实现时就按这个来，没有走动态添加路由的方案，因为那个方案刷新会闪。」

### 第 6 段：收尾（0.5 分钟）

**讲解要点**：

- 交付物：可运行的前后端工程 + 4 篇文档（工程介绍、测试报告、提示词记录、演示脚本）+ OpenSpec 规范。
- 测试结论：44 个验证点 43 项通过，1 项（看板筛选）为已知缺口并已记录。
- 遗留与改进方向：补自动化测试、看板加筛选、密码重置改邮件通知。

## 三、预设追问与应答

| 可能的提问 | 建议应答 |
|---|---|
| 为什么要用 `DECIMAL` 而不是 `double`？ | double 是二进制浮点，0.1+0.2 都得不到 0.3；金额必须精确到分，所以数据库用 DECIMAL(12,2)，Java 用 BigDecimal，统计走 SUM 聚合。 |
| JWT 和 Session 的取舍？ | 考核要求 JWT。无状态的好处是服务端不存会话、天然支持多实例；代价是无法主动踢人下线。本项目用 2 小时过期控制风险。 |
| 菜单权限和按钮权限怎么区分？ | 同一个 `sys_menu` 表，靠 `menu_type` 区分：1 目录、2 菜单、3 按钮。菜单决定侧边栏和路由，按钮只提供 `perms` 字符串用于显隐和接口校验。 |
| 普通用户能不能通过改前端代码越权？ | 能改前端隐藏/显示按钮，但后端每个接口都有 `@PreAuthorize`，权限不足返回 403，拿不到数据。前端只是体验层，真正的边界在后端。 |
| 管理员是怎么判定的？ | 角色编码 `role_code = 'admin'` 即为管理员，在 `UserDetailsServiceImpl` 里返回 `*:*:*` 通配权限。没有用 userId 硬编码，便于换账号。 |
| 统计为什么选"支出"时收入是 0？ | 统计与列表共用同一套筛选条件（含类型），这样数字才能和列表对得上。如果统计忽略类型，筛选后的列表和统计就对不上了。 |
| 软删除的数据还能恢复吗？ | 数据仍在表里，`is_deleted=1`。目前没有做恢复入口，加一个把字段改回 0 的接口即可。 |
| 操作日志会不会影响性能？ | 日志在 `finally` 里同步落库，单条 insert，对本地演示无影响。生产环境应改异步队列，且日志写入失败不能影响业务，代码里已 catch。 |
| 项目里有多少是 AI 写的？ | 约 80%，实体/Mapper/标准 CRUD/前端页面基本一次成型。人工集中在设计决策、验收测试、问题排查，比如 `menuIds` 语义缺陷、鉴权状态码不一致都是人工发现并修的。 |
| 如果并发改同一个角色权限会怎样？ | 目前是"先删后插"，无版本控制，并发时后写覆盖先写。改进方向是加乐观锁字段或在事务里先查后改。 |
| 看板缺口打算怎么补？ | 给 `/dashboard/stats` 加 `dateType` / `type` 入参，SQL 复用列表的筛选条件；前端在看板顶部加筛选栏，切换后重新拉取。改动量约半小时。 |
| 为什么没有单元测试？ | 时间优先投在功能完整性上，验收通过接口脚本 + 页面走查完成。后续会优先给 `RecordService` 的隔离逻辑和 `OperLogAspect` 补测试。 |
